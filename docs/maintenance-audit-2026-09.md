## Security & privacy audit

**Result: passed.** No secret has ever been committed to this repo.

### Method

```zsh
# 1. Secrets in the working tree
grep -rn -E "(api[_-]?key|secret|token|password|passwd|private[_-]?key|ssh-rsa|BEGIN [A-Z ]*PRIVATE KEY|ghp_|gho_|github_pat_|sk-[a-zA-Z0-9]{20,}|xox[bpoa]-|AKIA[0-9A-Z]{16})" . -i --exclude-dir=".git"

# 2. Files that shouldn't exist here at all
find . -not -path './.git/*' \( -name "*.env*" -o -name "*secret*" -o -name "*private*" -o -name "*.pem" -o -name "*.key" -o -name "id_*" \)

# 3. Full history, not just the working tree — the important one
git log --all --oneline -- "*.zshrc.secret" "*.zshrc.secrets" "*.env" "*id_rsa*" "*id_ed25519*" "*.pem" "*.key"
```

### Findings

- **History is clean.** Check 3 returns empty: no secrets file, private key,
  or `.env` has ever been committed, in any commit, on any branch.
- **Working tree is clean.** Every hit from check 1 was a safe reference:
  `tools/.npmrc` uses `${GITHUB_TOKEN}` (an env var, not a literal — fixed
  earlier in `d361f53`), and the rest are test assertions in
  `scripts/test/assertions.sh` and the committed `.template` file.
- **The live secrets file is correctly excluded.** `~/.zshrc.secret` exists
  outside the repo at mode `0600`, and `.gitignore` catches both the
  singular and plural spellings via `*secret*`.

### Audited after the fact: the 2026-09-01 auto-backup

`ee42610` ("backup 2026-09-01 08:56") was generated by `dotbackup` and
**pushed 253 new lines of `shell/.zshrc` to a public repo before review.**
Because a live `.zshrc` is exactly the kind of file that accumulates
credentials, it was audited line by line retroactively.

**It was clean.** The additions are a large `syshealth()` shell function
(CPU/memory/disk/process/network reporting) plus two `export` lines. No
credentials, no API keys, no IP addresses, no email addresses, no internal
hostnames. Nothing needed to be redacted or history-rewritten.

This is worth repeating as a risk, not a reassurance: an automated
`dotbackup` can push whatever is in the live file to a public repo without a
human seeing it first. It happened to be safe this time.

## Fallout from the moves

The `~/scripts` → `~/dev/projects/scripts/` move broke several paths. Two
were fixed in `ccc99a1`; two remain open.

**Fixed:** the LaunchAgent plist (`macos/com.pieterdejong.weeklycleanup.plist`)
and the three stale `~/scripts/...` references in `docs/weekly-cleanup.md`.
The plist now matches the loaded LaunchAgent in `~/Library/LaunchAgents/`,
and `docs/mac-maintenance.md` already ran the script directly out of the repo,
so it needed no change.

**Still open** — tracked in the [README TODO list](../README.md#-known-todos):

1. **Secrets filename mismatch (singular vs plural).** The live and tracked
   `shell/.zshrc` sources `~/.zshrc.secret` (singular, line 2) — that is the
   file that exists and holds the real values. But
   `shell/.zshrc.secrets.template`, the README's "Secrets pattern" section,
   and `scripts/test/assertions.sh:56` all expect `.zshrc.secrets` (plural),
   **so that assertion currently fails.** Not a security hole — `.gitignore`
   covers both spellings and nothing has ever been committed. The fix is to
   pick one name. Aligning the docs, template and test to the *singular*
   reality is the lower-risk direction, since it never touches a live file
   holding real credentials.
2. **`shell/.zshrc` sources a dead path.** Line 373 is
   `[[ -f ~/scripts/ollm.zsh ]] && source ~/scripts/ollm.zsh`. That path no
   longer exists — the file now lives at `~/dev/projects/scripts/ollm.zsh` —
   so the guard silently fails and the file is never sourced. Fix the path in
   the **live** `~/.zshrc`, then run `dotbackup`.

## The hazard that caused most of this

Documented in full in [LEARNINGS.md](../LEARNINGS.md#issue-edits-made-in-the-repo-silently-disappear-after-dotbackup).
Summarised here because it explains why several items above had to be
reopened:

**`dotbackup` flows one way — live → repo.** It copies `~/.zshrc` over
`shell/.zshrc` wholesale. Any edit made to the *repo* copy that was not also
made to the live file in `~` is silently overwritten on the next backup.

On 2026-08-31 the secrets-sourcing line was added to the repo copy and the
README was updated to say so. The 2026-09-01 backup reverted the code change
— but **not** the README, because docs aren't overwritten by `dotbackup`.
The result was documentation confidently describing a state the repo was no
longer in, which is precisely the failure mode to watch for. Verify against
the live file, not the README.
